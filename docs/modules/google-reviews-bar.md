# Google reviews bar and the header column

Moved out of `AGENTS.md` section 1, item 7, verbatim, so the instruction file stays short. The rules below are binding exactly as before; `AGENTS.md` keeps the summary and links here.

7. **The header is one centred column, and the Google rating follows Google's own row**: the utility bar ([`components/layout/LiveMetarBar.tsx`](components/layout/LiveMetarBar.tsx)) and the navbar share one `max-w-7xl` column, and the reviews and the quick links form one centred cluster instead of sitting at opposite screen edges (`tests/usability/google-reviews-utility-bar.spec.ts` measures it at 1558px). **The utility bar is the only place Google reviews render**: there is no home-page carousel or any second copy, and nothing may add one. With review data the bar shows a large score, five stars filled to the rating and a grey localized count (for example `4.9 ★★★★★ 127 reviews`), and a click opens a scrollable dropdown displaying all available Google reviews in true chronological order (newest first), never Google's "most relevant" pick, each with Google's author attribution (avatar, name, profile link), its publish date and relative time, Google's translation into the page language with a "Show original" switch and a "Translated by Google" notice (`/api/reviews?language=`; the parameter is `language`, never `lang`, because Wix Multilingual owns `?lang=` on the Wix-hosted site and 301-strips `?lang=he`, which would hand Hebrew visitors the English default; `lang` remains a read-only legacy alias on `/api/reviews` and `/api/blog`), plus the ordering notice and a link to Google's review policy that the Places policies require. **Google is read on the twice-a-day cadence, never per page view**: `.github/workflows/google-reviews-snapshot.yml` fires at 03:07, 04:07, 14:07 and 15:07 UTC, `scripts/google-reviews-snapshot-hour.mjs` lets through only the runs whose Israel hour (Asia/Jerusalem, both daylight-saving offsets) is 06 or 17, and the run calls `POST /api/reviews/refresh` on the host in the repository variable `REVIEWS_REFRESH_HOST` with the repository secret `REVIEWS_REFRESH_TOKEN` as a Bearer token (the same value must be set on the Wix site with `wix env set REVIEWS_REFRESH_TOKEN`; the route compares it with `constantTimeEqual()` and answers 503 while it is missing or shorter than 32 characters and 401 to anyone else; the workflow skips with a notice while the secret is missing). The refresh reads the **legacy Place Details web service with `reviews_sort=newest`** and the field list `reviews,rating,user_ratings_total` (Places API (New) returns only five relevance-ranked reviews and has no sort parameter), once and untranslated: **Google Places never translates reviews** (asked for a language it only selects reviews written in it, verified live 2026-11-11), so the translation under "Translated by Google" comes from **Google Cloud Translation (Basic v2)**, `lib/reviews/review-translation.ts`, one request per page language carrying the reviews not written in it (`format: text`, Google detects the source; Hebrew's `iw`/`yi` tags map to `he`). The same API key serves both (`GOOGLE_TRANSLATE_API_KEY` overrides it); the Cloud project needs "Cloud Translation API" enabled and allowed in the key's API restriction. If translation is unavailable the originals are served as written and the snapshot source says so, never an empty bar. The refresh re-sorts by publish time with `sortNewestFirst()`, drops star-only reviews, and stores one row in `google_reviews_snapshot` (migration `009_google_reviews_snapshot.sql`; Supabase in production, fail-closed without it, in-memory for development and tests). `GET /api/reviews?language=` serves that stored snapshot (one 60 s in-process memo) and the bar fetches it on every page load and when a tab is shown again; the count is never hard-coded. **Without a stored snapshot** (no refresh yet, or no snapshot store at all, which is the case while the Wix site has no Supabase variables) the server keeps the same cadence itself: `getCachedGoogleReviews()` reads Google once per process per 06:00/17:00 Israel window (`lib/reviews/snapshot-window.ts`, `snapshotWindowId()`), with the same newest-first source, shares that read between concurrent requests and serves it until the next boundary, keeping the previous window if Google refuses; visitors therefore always see live newest-first reviews and the stored snapshot only removes the per-process reads. Only with no `GOOGLE_PLACES_API_KEY`, or when Google refuses the very first read of a cold process, does the bar fall back and still show five yellow stars filled to the grade (all five while it is 5.0), the grade and the count as a plain link to the Google profile, taken from the labelled last-known aggregate `LAST_KNOWN_GOOGLE_RATING` (exported by `lib/reviews/use-google-reviews.ts`, stored as two numbers in `lib/reviews/last-known-rating.json`; never add review texts to it). Do not edit those numbers by hand or pin them in a test: `.github/workflows/google-rating-refresh.yml` runs `scripts/refresh-google-rating.mjs` weekly, reads the official Places API (New) with field mask `rating,userRatingCount` (never a scrape of google.com/maps) and opens one rolling `automation/google-rating` pull request. It needs the `GOOGLE_PLACES_API_KEY` repository secret and only skips with a notice while that is missing; the owner merges the PR by hand, because a merge made by github-actions never starts Verify on `main` and Release Please would not see it. The JSON is excluded from the Genesis fingerprint (`VOLATILE_DATA` in `scripts/check-genesis-coverage.ts`), and the Playwright and Vitest specs read it instead of hard-coding it. Google's own numbers replace it on every load, and `/api/reviews` itself still reports only what Google returned (`tests/a11y/google-reviews-bar.spec.ts` holds both states to zero axe violations). On phones from 360px the WhatsApp action sits beside Book in the navbar (between the logo and the menu) so the top bar fits the rating, the social icons and the language selector on one row without overlap; below 360px it stays in the top bar, and from `md` up it is always in the top bar. On phones the footer is absent, so the localized "About" group of the mobile menu also carries "Cookie settings" (`ConsentSettingsLink`); the header's markup, ids and test hooks live in `components/layout/navbar/` and are changed there, never by growing `Navbar.tsx` (`tests/unit/module-size.test.ts` keeps it under 400 lines).
